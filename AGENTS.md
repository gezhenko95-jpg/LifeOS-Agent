# Конституция проекта LifeOS Agent

Этот документ является главным законом и руководящим стандартом разработки проекта **LifeOS Agent**. Все разработчики и ИИ-агенты (Subagents) обязаны строго следовать описанным ниже принципам и правилам.

---

## 1. Философия и Миссия

1.  **AI Chief of Staff, а не чат-бот:**
    LifeOS Agent — это не просто чат-интерфейс для генерации текста. Это ваш высокоэффективный руководитель штаба (Chief of Staff), который управляет процессами, координирует задачи, фильтрует информацию, принимает решения на основе контекста и действует проактивно в интересах пользователя.
2.  **Минимизация когнитивной нагрузки:**
    Главная цель системы — уменьшать когнитивную нагрузку на пользователя. Интерфейсы, уведомления, отчёты и действия агента должны быть максимально лаконичными, точечными и избавленными от "шума". Система должна предлагать готовые решения или выполнять рутину незаметно, требуя внимания человека только в критические моменты.
3.  **Принцип достаточности ИИ (Простой код > LLM):**
    **Запрещено** использовать большие языковые модели (LLM) там, где задачу можно решить классическим детерминированным кодом (алгоритмы, регулярные выражения, правила, шаблонизаторы). LLM привлекаются только для задач с высокой степенью неопределенности (анализ естественного языка, сложные рассуждения, синтез неструктурированных данных).

---

## 2. Стек технологий и Архитектура

1.  **Исключительно Python:**
    Весь бэкенд и сервисы проекта пишутся строго на языке **Python**. Использование других языков программирования не допускается.
2.  **FastAPI + PostgreSQL:**
    Основным технологическим стеком для разработки API и сервисов является **FastAPI** в качестве веб-фреймворка и **PostgreSQL** в качестве реляционной базы данных.
3.  **Запрет прямого доступа AI к базе данных:**
    ИИ-агенты (LLM-компоненты во время работы приложения) **никогда не работают с базой данных напрямую**. Все взаимодействия должны происходить строго через защищенный, строго типизированный слой API (сервисы, репозитории), который контролирует права доступа, валидирует входные данные и логирует изменения.
4.  **Каждая возможность — отдельный сервис:**
    Новые функции или крупные блоки возможностей не должны перегружать существующие модули. Каждая новая бизнес-возможность (feature) проектируется и реализуется в виде независимого, изолированного сервиса.
5.  **Ограничение на размер файлов (No Large Files):**
    Запрещено создавать и поддерживать большие файлы. Код должен быть максимально декомпозирован. Если файл (модуль) превышает **250-300 строк кода**, он должен быть разделен на несколько логических подмодулей или классов.

---

## 3. Процесс разработки и Проектирование

1.  **Сначала спецификация в `/specs`:**
    Любая новая функция или сервис сначала подробно описывается в файле формата Markdown в директории `/specs` в корне проекта. Реализация кода начинается **только после** утверждения спецификации пользователем. Спецификация должна включать:
    *   Описание бизнес-требований и сценариев использования.
    *   Схему данных и API контракты.
    *   План тестирования и критерии готовности (Definition of Done).
2.  **Запрет несогласованных изменений архитектуры:**
    Запрещено вносить изменения в базовую архитектуру, общие интерфейсы, схемы базы данных или глобальные соглашения без явного предварительного обсуждения и утверждения с пользователем.
3.  **Тестирование обязано быть:**
    Любой новый сервис или функция должны быть покрыты автоматическими тестами (юнит- и интеграционными) минимум на 80%.

---

## 4. Качество кода и Стандарты

*   **Типизация:** Использование type hints (аннотаций типов) в Python является обязательным для всех функций, методов и переменных. Чистый и строгий Python с проверкой типов (Mypy).
*   **Линтинг и Форматирование:** Код должен соответствовать PEP 8. Для форматирования и линтинга используются `ruff` или `black` + `flake8`.
*   **Безопасность:** Секреты хранятся только в `.env` (который обязательно занесен в `.gitignore`). Код не должен содержать hardcoded ключей и токенов.

---

## 5. Протокол работы для ИИ-разработчиков (Subagents)

1.  **Исследование:** Ознакомиться с `AGENTS.md` и спецификациями в `/specs`.
2.  **Проектирование:** Создать черновик спецификации в `/specs/[feature_name].md` и дождаться аппрува.
3.  **Реализация:** Написать изолированный код сервиса на Python (FastAPI). Помнить об ограничениях на размер файлов.
4.  **Валидация:** Написать тесты, убедиться, что линтеры и тесты проходят успешно.
5.  **Документирование:** Зафиксировать изменения в приватной памяти или истории коммитов.
