## 1. Критические ошибки (чинить немедленно)

### C-1. Postgres открыт в интернет с паролем `postgres`

> **Уточнение о доказательствах.** Первоначально я пометил этот пункт как
> подтверждённый живым коннектом — это было неверно: мой внешний
> TCP-probe оказался ложноположительным (порт 12345, который никогда не
> открывался, «отвечал» так же — где-то по пути middlebox принимает любой
> коннект). Прямого доказательства именно для 5432 у меня нет.
>
> Косвенные доказательства остаются весомыми: `docker-compose.yml`
> публиковал `5432:5432` на `0.0.0.0`, а обход ufw докером подтверждён
> для соседнего порта 8000 **надёжно** — `curl http://148.135.208.126:8000/health`
> возвращал реальный JSON при активном ufw, разрешающем только 22/80/443
> (после фикса тот же curl не отвечает). Механизм у обоих портов один.

`docker-compose.yml:9-10` публикует `5432:5432`. На сервере `ufw` активен
и разрешает только 22/80/443 — **но Docker пишет свои правила в цепочку
`DOCKER` таблицы `nat`, минуя `INPUT`, где работает ufw**. Классическая
ловушка «Docker обходит UFW».

Проверено с локальной машины: TCP-коннект на `148.135.208.126:5432`
проходит. Пароль роли — `postgres` (он же захардкожен в
`database_url` в `docker-compose.yml:24,37`, иначе приложение бы не
подключилось).

**Последствие:** любой в интернете читает и меняет всю БД — дневник,
задачи, цели, память. Полная компрометация данных.

**Фикс** (`docker-compose.yml`):
```yaml
  db:
    ports:
      - "127.0.0.1:5432:5432"   # или убрать блок ports целиком
```
`api`/`bot` ходят в БД по внутренней docker-сети (`db:5432`), проброс
наружу не нужен вообще. Плюс сменить пароль (`ALTER USER postgres ...`
+ `.env`).

### C-2. 🔴 ПОДТВЕРЖДЕНО. REST API без аутентификации, дневник читает любой

`app/main.py:35-40` подключает роутеры без единой проверки доступа.
`telegram_user_id` — обычный query-параметр (`app/api/tasks.py:47`,
`app/api/memory.py:45`, `app/api/watchlist.py:43`, аналогично
habits/goals).

Проверено:
```
curl https://lifeos-agent.ru/memory?telegram_user_id=414825951
```
→ вернул личные дневниковые записи в открытом виде. `DELETE /memory/{id}`
и `PATCH` тоже никем не защищены — данные можно не только прочитать, но и
стереть.

**Фикс (минимальный, 20 строк):** общий токен в заголовке.
1. `Settings.api_token: str = ""` в `app/core/config.py`.
2. Зависимость:
```python
# app/api/deps.py
async def require_token(x_api_token: str = Header("")) -> None:
    expected = get_settings().api_token
    if not expected or not secrets.compare_digest(x_api_token, expected):
        raise HTTPException(status.HTTP_401_UNAUTHORIZED)
```
3. `dependencies=[Depends(require_token)]` на каждый `include_router`
   (кроме `health`).
4. В `app/web/static/index.html` токен уже вводится по образцу
   `STORAGE_KEY` (строка 220) — добавить второе поле «токен», класть в
   `localStorage` и слать заголовком из `api()` (строка 236).

Правильнее — Telegram Login Widget, но это отдельная фича; токен закрывает
дыру сегодня.

### C-3. 🔴 ПОДТВЕРЖДЕНО. Порт 8000 открыт напрямую, HTTPS в обход

Тот же обход ufw: `curl http://148.135.208.126:8000/health` отвечает.
Значит весь API (и `/ui`) доступен **по plain HTTP**, мимо Caddy — токен

**Фикс:** `- "127.0.0.1:8000:8000"` в `docker-compose.yml:26-27`. Caddy

### C-4. Бот отвечает кому угодно, а не только владельцу

Проект single-user (PROJECT.md), но нигде — ни в `app/telegram/bot.py`,
ни в `handlers.py`, ни в `callbacks.py` — нет проверки
`update.effective_user.id == settings.owner_telegram_user_id`.

Последствия, по возрастанию неприятности:
- посторонний тратит **ваши** деньги на OpenRouter (каждое сообщение →
  AI-фолбэк, каждое фото → vision-запрос);
- `handle_photo_message` (`handlers.py:126`) грузит **чужие фото на ваш
  личный Google Drive** в папку `LifeOS/`;
- `TaskService.list_due_reminders()` (`app/tasks/service.py:175`) намеренно
  **не фильтрует по пользователю** — значит напоминания о задачах чужака
  прилетят вам в чат (утечка данных в обе стороны);
- `MemoryRepository.list_missing_embeddings` (`repository.py:78`) так же
  без фильтра — вы оплачиваете embeddings чужих записей.

**Фикс:** один фильтр на все хендлеры в `bot.py`:
```python
owner = filters.User(user_id=settings.owner_telegram_user_id)
application.add_handler(MessageHandler(filters.TEXT & ~filters.COMMAND & owner, ...))
application.add_handler(MessageHandler(filters.PHOTO & owner, ...))
application.add_handler(CallbackQueryHandler(handle_callback_query, ...))  # + проверка внутри
application.add_handler(CommandHandler("start", start_command, filters=owner))
```
`/start` стоит оставить открытым — он показывает Telegram ID, это нужно
для первичной настройки; но отвечать он должен только текстом ID.

### C-5. Токен бота и содержимое дневника утекают в логи контейнера

`app/db/session.py:16` — `echo=True` («для отладки в development») работает
на **проде**: каждый SQL-запрос с параметрами пишется в лог, включая тексты
дневниковых записей.

Плюс `logging.basicConfig(level=logging.INFO)` (`app/telegram/runner.py`)
включает INFO у `httpx`, а тот логирует полный URL запроса к Telegram —
**вместе с токеном бота**:
```
INFO:httpx:HTTP Request: POST https://api.telegram.org/bot<ТОКЕН>/getUpdates
```
Проверено в живых логах. Ротации логов нет (`json-file` по умолчанию
безлимитный) — ~8 МБ/сутки мусора, почти весь от `echo=True`.

**Фикс:**
```python
# app/db/session.py
engine = create_async_engine(settings.database_url, echo=settings.environment == "development")
```
```python
# app/telegram/runner.py
logging.getLogger("httpx").setLevel(logging.WARNING)
```
```yaml
# docker-compose.yml — каждому сервису
    logging: { driver: json-file, options: { max-size: "10m", max-file: "3" } }
```
Токен уже засветился в логах — после фикса имеет смысл перевыпустить его
в @BotFather.

## 2. Архитектурные проблемы

### A-1. Слой авторизации отсутствует как понятие

`ARCHITECTURE.md` описывает `API/Telegram → Service → Repository → DB`, но
в этой цепочке нет места, где решается «а можно ли этому пользователю
трогать эту сущность». Отсюда C-2 и C-4, а также все IDOR ниже (B-2).

Сервисы, которые работают по `id` — `update_task(task_id)`,
`delete_task(task_id)`, `mark_done(item_id)`, `delete_habit(habit_id)`,
`complete_goal(goal_id)` — **не принимают `telegram_user_id` вообще**, то
есть проверить владельца физически негде. Это не косметика: сигнатуры
надо менять.

Рекомендация: `update_task(telegram_user_id, task_id, ...)` и проверка
`task.telegram_user_id == telegram_user_id` внутри сервиса. Единый шаблон
для всех пяти доменов.

### A-2. Сессия БД живёт дольше, чем нужно, и коммитит чужие изменения

`Repository.save()` во всех репозиториях — это просто
`await self._session.commit()` без привязки к объекту
(`app/tasks/repository.py:42`, `memory/repository.py:91`, и т.д.). Внутри
одного `async with AsyncSessionLocal()` в `_reply_via_engine` живут 5
сервисов сразу — любой `save()` коммитит **все** незакоммиченные
изменения всех остальных. Пока работает, потому что операций мало, но это
мина: частичный откат невозможен, «сохранить задачу» может втихую
зафиксировать наполовину изменённую цель.

### A-3. Сборка сервисов дублируется в 7 местах вместо DI

`_reply_via_engine` (`handlers.py:353-368`) руками собирает 5 сервисов и
4-аргументный `PendingPromptService`. Ровно то же — в `jobs.py` четыре
раза, в `callbacks.py`, в `_send_insights`. Добавление шестого сервиса в
`ConversationEngine` = правка семи мест.

Нужна одна фабрика:
```python
# app/core/container.py
def build_engine(session) -> ConversationEngine: ...
def build_prompt_service(session) -> PendingPromptService: ...
```

### A-4. `ConversationEngine` знает про Telegram через регулярку

`handlers.py:69` — `_TASK_CREATED_PATTERN` парсит **русский текст ответа**
движка, чтобы понять «задача создана» и подцепить кнопки. Движок объявлен
Telegram-агностичным, и формально это так, но связь есть — она просто
хрупкая: поправите формулировку в `engine.py:262` («Добавил задачу: …») —
кнопки молча исчезнут, тесты этого не увидят.

Правильно: `handle_message` возвращает не `str`, а
`EngineResult(text: str, created_task: Task | None)`. Telegram-слой сам
решает, что с этим делать. Движок остаётся агностичным по-настоящему.

### A-5. `parse_intent` вызывается дважды на каждое сообщение

`handlers.py:218` разбирает текст, чтобы перехватить LIST_*, потом
`engine.handle_message` (`engine.py:91`) разбирает **тот же текст заново**.
Дёшево по CPU, дорого по логике: два места, где «что делать с этим
сообщением», и они уже разъехались (см. B-1).

### A-6. Три параллельных механизма «что делать с сообщением»

`_MENU_ACTIONS` (точное совпадение) → `parse_intent` в handlers →
`parse_intent` в движке → AI-фолбэк. Плюс перехват pending journal
**раньше** всего этого. Порядок нигде не описан одним куском; отсюда баг
B-1, который живёт в проде прямо сейчас.

## 3. Возможные баги (часть уже проявилась)

### B-1. 🔴 В проде: `/help` записался в дневник вместо справки

В боевой БД лежит запись `{"id":9, "type":"journal", "content":"/help",
"source":"quick_capture"}` — я её увидел через открытый API (C-2).

Механизм: `help_command` (`handlers.py:110`) идёт через `_reply_via_engine`,
а `_try_capture_journal` (`engine.py:122`) стоит **до** `parse_intent` и
глотает вообще любой текст, если открыт journal-pending. Команда попадает
в дневник, справка не показывается.

**Фикс:** в `_try_capture_journal` не перехватывать текст, начинающийся с
`/`, и не гонять `help_command` через движок (он не нуждается в БД —
можно отвечать `_HELP_TEXT` напрямую).

### B-2. IDOR в inline-кнопках

`callbacks.py:88-108` берёт `item_id` из `callback_data` и передаёт в
`service.update_task(int(item_id))` **без проверки владельца**. Любой, кто
пишет боту (см. C-4), может перебором id выполнять/удалять ваши задачи,
привычки, цели и watchlist. Лечится вместе с A-1.

### B-3. Падение на кривом `callback_data`

`parse_callback("мусор")` (`callbacks.py:41`) → `ValueError: not enough
values to unpack`. `int(item_id)` при пустом id — тоже `ValueError`.
Обработчика ошибок нет (`application.add_error_handler` не вызывается
нигде), значит исключение уходит в лог, а пользователь не получает ничего
— бот «молча завис».

**Фикс:** `add_error_handler` в `bot.py` + `try/except ValueError` в
`parse_callback` (возвращать `None` и выходить).

### B-4. `edit_message_text` с тем же текстом → BadRequest

`callbacks.py:83`. Нажали «🗑» на единственной задаче, потом ещё раз на
уже перерисованном пустом списке — Telegram отвечает
`Message is not modified`, исключение не ловится (см. B-3). Проявляется
регулярно при двойном тапе.

### B-5. Изменение записи памяти не сбрасывает embedding

`MemoryService.update` (`service.py:44-58`) меняет `content`, но
`embedding` остаётся от старого текста. Семантический поиск будет вечно
находить запись по её прежнему смыслу. Строчка фикса:
```python
if content is not None and content != entry.content:
    entry.content = content
    entry.embedding = None   # фоновая job пересчитает
```

### B-6. Подстрочные триггеры парсера ловят слова внутри фраз

`parser.py` матчит `keyword in lowered` без границ слова:
- «нужна **помощь** с отчётом» → HELP вместо задачи (`_HELP_KEYWORDS`);
- «**сделал** заметку — купить молоко» → COMPLETE_TASK;
- «**покажи** презентацию клиенту» → LIST_TASKS;
- «отдать **книгу** Пете» → в watchlist вместо задачи.

Часть компромиссов задокументирована в комментариях как осознанная
(ADR-004), но цена растёт вместе со списком триггеров — их уже 14 только
в `_WATCHLIST_TRIGGERS`. Минимальное улучшение без переписывания: границы
слов (`\bпомощь\b`) и якорь на начало сообщения для командных слов
(«удали», «выполнил», «покажи» — команда почти всегда в начале).

### B-7. `dd.mm` без года уезжает в прошлое

`date_parser.py:96-108`: «встреча 05.01», написанная в декабре, даст 5
января **текущего** года — дата в прошлом, задача мгновенно просрочена и
тут же выстрелит напоминанием. Нужно: если получившаяся дата раньше
сегодня и год не был указан явно — прибавить год.

### B-8. Дата + время не комбинируются

Задокументировано в `date_parser.py:9-12`: «завтра в 15:00» разбирается
только как «завтра, 09:00». Для ассистента с напоминаниями это заметная
дыра — время встреч указывают именно так.

### B-9. Синхронный Google Drive блокирует весь бот

`app/drive/client.py` использует `googleapiclient` (синхронный, на
`httplib2`) и вызывается прямо из async-хендлера
(`media_inbox/service.py:63-66`). На время загрузки фото — а это
несколько секунд — **весь event loop стоит**: бот не отвечает никому,
джобы не запускаются. Плюс `get_drive_client()` вызывается на каждое
фото (`handlers.py:143`) и каждый раз заново читает token.json и строит
discovery-клиент.

**Фикс:** обернуть в `asyncio.to_thread(...)` и закешировать клиент
(`@lru_cache` на `get_drive_client`).

### B-10. Списки молча обрезаются на 10

`keyboards.py:26` `_MAX_ITEMS = 10`. Задачи 11+ не показываются и никак не
упоминаются — пользователь думает, что их нет. Нужна хотя бы строка
«…и ещё N» или пагинация.

### B-11. Гонка на `pending_prompts` при пересечении джоб

14:00 (`send_midday_checkin_job`) и 19:00 делают `upsert`, затирая чужой
неотвеченный вопрос. Сейчас слоты разнесены, но `_EVENING_GAP_CHANCE`
уже создаёт вторую точку записи; при добавлении новых слотов ответ
пользователя будет разбираться в контексте не того вопроса.

## 6. Производительность

### P-1. N+1 по логам привычек — самое горячее место

`HabitService.get_streak` / `get_longest_streak` / `get_completed_days` /
`days_since_last_completion` — каждая тянет **все** логи привычки
(`repository.list_logs`) и считает в Python.

`build_habits_message` вызывает `get_streak` в цикле (`handlers.py:253`),
`InsightsService` — `get_completed_days` **и** `get_longest_streak` на
привычку (`insights/service.py:100,127`). При 10 привычках и годе истории
это 20+ полных выборок на один показ инсайтов.

**Фикс:** `list_logs_for_habits(habit_ids)` одним запросом + расчёт стриков
из общего словаря. Индекс `(habit_id, completed_on)` уже есть через
`UniqueConstraint`.

### P-2. Поиск и фильтрация целиком в Python

- `MemoryService.search` (`service.py:81`) грузит **все** записи
  пользователя и фильтрует `in` по строке. Заменяется на
  `WHERE content ILIKE :q` — одна строка.
- `TaskService.find_active_by_title` (`service.py:127`) — то же с задачами.
- `ConversationEngine._list_tasks_by_date` (`engine.py:284`) вытягивает все
  активные задачи и фильтрует по дате в Python.

### P-3. Семантический поиск не масштабируется

`semantic_search` (`memory/service.py:104`) загружает **все** записи с
embedding, каждый — 1536 float в JSON-колонке. На 1000 записях это ~12 МБ
JSON-парсинга на один запрос «напомни про…», в синхронном Python, внутри
event loop. Осознанное решение (spec 011: «без pgvector»), но потолок —
сотни записей, не тысячи. Дешёвый паллиатив до pgvector: хранить вектор
как `bytea` (`numpy.float32.tobytes()`) и считать через `numpy` — в 10-20
раз быстрее и в 4 раза меньше по объёму.

### P-4. Новый TCP+TLS на каждый вызов AI

`ai/client.py:48,75` — `async with httpx.AsyncClient()` внутри каждого
метода. На каждый запрос к OpenRouter — новое соединение и TLS-хендшейк
(+100-300 мс). Держать один `AsyncClient` на жизнь процесса.

### P-5. `echo=True` (см. C-5)

Логирование каждого SQL с параметрами — это ещё и заметный оверхед на
форматирование строк в горячем пути.

### P-6. Нет индексов под реальные запросы

`tasks`: индекс есть только на `telegram_user_id`. Частые запросы —
`(telegram_user_id, status)` и `(status, due_date, reminded_at)`
(джоба напоминаний, раз в минуту). `memory_entries`: нужен частичный
индекс `WHERE embedding IS NULL` для `list_missing_embeddings`.

## 7. Безопасность (кроме критических C-1…C-5)

- **CORS `allow_origins=["*"]` вместе с `allow_credentials=True`**
  (`main.py:26-32`). Спецификация запрещает такую пару, браузеры её
  игнорируют — но TODO в коде висит, а после C-2 это станет реальной
  проблемой. Заменить на `["https://lifeos-agent.ru"]`.
- **`/docs`, `/redoc`, `/openapi.json` открыты** (`main.py:19-22`) —
  публично отдают полную карту API. Выключить в проде.
- **Нет ограничения длины входящего сообщения** — текст любой длины
  уходит в AI-фолбэк и в `embed()`. Telegram допускает 4096 символов;
  умножьте на возможность слать их подряд (C-4).
- **Нет rate limiting** ни на API, ни на бота.
- **Prompt injection в `ai_extract`** (`proactive/ai_extract.py:96`):
  ответ пользователя вклеивается в промпт без экранирования, а результат
  напрямую создаёт цели/привычки/записи памяти. Для single-user это
  теоретически, но вместе с C-4 — практический вектор.
- **`token.json` монтируется в контейнер** `:ro` — правильно. Но
  `credentials.json` и `token.json` лежат в `/opt/lifeos/` рядом с кодом;
  права на файлы стоит проверить (`chmod 600`).
- **Пароль БД в открытом виде в `docker-compose.yml`** (строки 7, 24, 37),
  который коммитится в git. Вынести в `.env` (`${POSTGRES_PASSWORD}`).

## 8. Идеи рефакторинга

1. **`EngineResult` вместо `str`** (см. A-4) — снимает регулярку из
   `handlers.py` и открывает дорогу к другим каналам (голос, веб-чат).
2. **`app/core/container.py`** — единая сборка сервисов (A-3). Предпосылка
   почти для всех остальных улучшений.
3. **`BaseRepository[T]`** — минус ~150 строк дублирования (раздел 4).
4. **Единый `IntentRouter`** вместо трёх параллельных механизмов (A-6):
   один список правил `(matcher, handler)`, один проход, один порядок,
   который видно целиком.
5. **Авторизация как слой** (A-1): `telegram_user_id` первым аргументом во
   все сервисные методы, работающие по id.
6. **Декоратор `@owner_job`** для джоб — снимает восемь копий преамбулы.
7. **`asyncio.to_thread` для Drive** (B-9) — и заодно общий подход к любой
   синхронной библиотеке (matplotlib в `charts.py` тоже блокирует loop,
   хотя и на ~200 мс).

подключён — час работы.

## Что хорошо (чтобы не сломать при рефакторинге)

Аудит перечисляет проблемы, но по коду видно и обратное — это заметно
выше среднего для персонального проекта:

- **483 теста, все зелёные**, `ruff` и `black` чисто. Тесты покрывают
  бизнес-логику, а не геттеры.
- **Комментарии объясняют «почему», а не «что»** — и почти каждый
  нетривиальный кусок ссылается на реальный баг или спеку. Это редкость.
- **Чистые функции вынесены и тестируются без моков**
  (`insights/calculations.py`, `memory/embeddings.py`, `scheduler/charts.py`).
- **AI-фолбэки везде «тихие»** — ни один сбой OpenRouter не роняет
  пользовательский сценарий. Принцип выдержан последовательно.
- **ADR-004 реально соблюдается**: статистика, стрики, gap-detection —
  обычный Python, LLM только там, где без него никак.
- Слои `Service`/`Repository` разделены честно, бизнес-логики в API нет.

Главный вывод: **код в порядке, дыра — в инфраструктуре и в отсутствии
слоя авторизации.** Пункты 1-6 плана закрывают всё критическое и не
требуют трогать бизнес-логику.
