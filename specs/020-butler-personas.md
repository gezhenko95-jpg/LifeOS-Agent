# Butler Personas Specification

---

# Цель

Корневая проблема — не нехватка фич, а то, что ботом почти не пользуются
(владелец прямым текстом, продолжение находки specs/016-engagement-hooks:
«реально пользуюсь только дайджестами, задачи/цели не ставлю»). Гипотеза
этой итерации: бот должен ощущаться живым собеседником с характером,
который заинтересован в развитии владельца — не безликим генератором
списков. Решение — не новый домен данных, а **персонажный слой поверх
уже существующих AI-мест** в пяти файлах, плюс возможность переключить,
чей «характер» сейчас говорит.

Выбор режима — **только на сайте** (`/ui`), не в боте. Голосовой ввод не
трогаем (остаётся выключен, specs/012). Частоту push-сообщений **не
увеличиваем** — специально отклонённый вариант (см. «Что НЕ входит»).

---

# Бизнес-требования

- 4 персонажа, один активен в любой момент: **Дворецкий** (по умолчанию),
  **Тренер**, **Директор**, **Финансист**;
- переключение — сегмент-контрол или дропдаун на `/ui`, действует сразу
  на все последующие AI-сообщения; в боте переключателя нет;
- у каждого персонажа свой узнаваемый архетип и манера речи (не
  буквальные персонажи из книг/игр/фильмов — копирайт и разностилье пяти
  чужих голосов в одном боте, см. обсуждение с владельцем);
- AI-сообщения персонажа — **не односложные**: практичный, развёрнутый
  текст (2–4 предложения), не голая острота на 20 слов, как сейчас у
  `_generate_insight` в брифинге;
- персонаж должен уметь чуть-чуть поддержать разговор со владельцем и
  учитывать недавний контекст (что уже отмечено/сказано), не отвечать
  как в вакууме на каждую реплику;
- контекст ограничен окном (последние записи Memory + видимые данные
  дня) — не «помни вообще всё», чтобы стоимость AI-вызовов не росла
  без границ со временем (см. переписку с владельцем про cost);
- специфичные для персонажа темы (тренер спрашивает вес/подходы,
  напоминает размяться; директор предлагает бизнес-идеи; финансист
  следит за нормами) — это НЕ отдельная инженерия под каждую тему, а
  ожидаемый побочный эффект того, что практичный AI-совет генерируется
  с учётом характера и уже собранных данных нужного домена (привычки/
  цели/финансы) — см. «Архитектура».

# Персонажи (`app/assistant/personas.py`)

Единый источник правды — характер-лист каждого персонажа как текстовая
константа (не дублируется по файлам-генераторам). Фрагмент вставляется
в начало system-промпта в каждом из пяти мест.

| Персонаж | Архетип-вдохновение (не дословно) | Манера | Фокус-домены |
|---|---|---|---|
| 🎩 Дворецкий *(default)* | невозмутимый английский дворецкий | спокойный, вежливый, сухой юмор, не паникует, держит баланс | все поровну |
| 🏋️ Тренер | капитан спортивной команды / коуч | энергичный, короткие фразы, спортивные метафоры, слегка подкалывает за пропуски | привычки, настроение |
| 💼 Директор | резкий бизнес-визионер / стартап-CEO | прямой, без сюсюканья, толкает к следующему шагу, ценит цифры | задачи, цели |
| 📊 Финансист | дотошный CFO | сухой, точный, любит конкретные суммы, констатирует факт без нотаций | финансы |

Обращение — на «ты» у всех, без китча/наигранности. Собственных имён
персонажи не получают в этой итерации — ярлык роли (см. «Что НЕ
входит»).

# Архитектура

## Новый домен `app/assistant/`

Восьмой домен по тому же шаблону, что crm/mood: `models.py` (одна
таблица `AssistantSettings`: `telegram_user_id` unique, `persona`
строкой, `updated_at`), `repository.py` (get-or-create с дефолтом
`butler`), `service.py` (`get_persona`/`set_persona`), `schemas.py`.
`personas.py` — константы характер-листов, без БД (см. таблицу выше).
Миграция `021_create_assistant_settings`. `core/container.py::
build_assistant_service`.

## Внедрение в существующие AI-места

Персонаж-параметр добавляется в пять функций, у каждой уже есть свой
`_SYSTEM_PROMPT`/`_INSIGHT_SYSTEM_PROMPT` и вызов `ai_client.complete`:

1. `app/scheduler/briefing.py::_generate_insight` (утренний брифинг)
2. `app/scheduler/evening_reflection.py` (вечерний вопрос)
3. `app/scheduler/finance_report.py` (еженедельный финансовый инсайт)
4. `app/scheduler/weekly_digest.py` (еженедельный дайджест-инсайт)
5. **Новое** — `app/conversation/chat_reply.py` (см. ниже)

Каждая функция получает опциональный `persona: Persona = Persona.BUTLER`
(тот же паттерн опциональности, что у `ai_client`/`rewards_service` в
`ConversationEngine`, см. HANDOFF раздел «Технические нюансы» — `None`/
дефолт тихо не ломает старые вызовы и тесты). Системный промпт
собирается как `_character_sheet(persona) + "\n\n" + <существующая
task-specific инструкция>`. Ограничение длины ответа переписывается с
«не более 20 слов» на «2–4 предложения, до ~70 слов, практично и
конкретно — не наблюдение, а совет/предложение по существу» — общее
для всех пяти мест, не только брифинга.

`telegram_user_id`, у которого уже есть сессия/сервисы в каждой job-
функции (`app/telegram/jobs.py`), подтягивает персонажа через
`AssistantService.get_persona` перед вызовом генератора — один
дополнительный запрос в БД на job, не на каждое сообщение.

## Новое: разговорный фолбэк (`app/conversation/chat_reply.py`)

Сейчас нераспознанное свободным текстом сообщение (не задача, не
привычка, не pending-ответ, не ADD_TASK-подобное для `ai_fallback.py`)
получает статичный `_HELP_TEXT` — список команд, не разговор. Новый
модуль подключается в `ConversationEngine` ПОСЛЕ существующих попыток
(pending prompt → rule-based → ai_fallback ADD_TASK) и ПЕРЕД
статичным help — то есть это последний, а не первый фолбэк, порядок
попыток не меняется, только добавляется новый шаг в конце цепочки.

Контекст для промпта — ограниченное окно, без новых таблиц в этой
итерации:
- последние `_MAX_MEMORY_ITEMS`-подобное число записей `MemoryEntry`
  (типы `journal`/`preference`/`project`) — уже существующий источник,
  просто новый читатель;
- краткая сводка «сегодня» (активные задачи/привычки/цели) — тот же
  запрос, что уже собирает `build_morning_briefing`, переиспользуется
  как контекст, не заново придумывается.

Если AI недоступен/упал — тихий откат на существующий `_HELP_TEXT`, как
и у всех AI-мест в проекте (никогда не ломает ответ пользователю).

# Модель данных (`app/assistant/models.py`)

## AssistantSettings

| Поле | Тип | Комментарий |
|---|---|---|
| `id` | int, PK | |
| `telegram_user_id` | BigInteger, unique, indexed | владелец |
| `persona` | String(20) | `butler`\|`trainer`\|`director`\|`financier`, default `butler` |
| `updated_at` | DateTime(tz) | `onupdate=func.now()` |

Одна строка на пользователя — get-or-create с дефолтом `butler` при
первом обращении (не требует отдельной команды «инициализировать»).

# API (`app/api/assistant.py`)

- `GET /assistant/persona?telegram_user_id=` — текущий персонаж (создаёт
  дефолтную запись, если её ещё нет)
- `PUT /assistant/persona` — `{telegram_user_id, persona}`, валидация
  значения по `Persona` enum

---

# `/ui`

Не отдельная вкладка (это настройка, не домен с данными) — компактный
переключатель персонажа в шапке или в блоке настроек, всегда на виду
(сегмент-контрол из 4 иконок-подписей: 🎩/🏋️/💼/📊). Смена — сразу PUT-
запрос, без формы/подтверждения.

# Что НЕ входит (в эту итерацию)

- голосовой ввод — не трогаем, остаётся выключен (specs/012);
- увеличение числа push-слотов в день — явное решение владельца
  («не увеличивать, рекомендую» из обсуждения), персонаж делает
  СУЩЕСТВУЮЩИЕ сообщения живее, не добавляет новые;
- случайные незапланированные сообщения вне расписания — обсуждалось,
  сознательно отложено вместе с пред. пунктом;
- буквальные персонажи из книг/игр/фильмов — копирайт + разностилье;
- собственные имена персонажей — только ярлыки-роли;
- долгая семантическая память / эмбеддинги / pgvector — контекст
  ограничен последними записями Memory и сводкой дня, без векторного
  поиска (P-3 из AUDIT.md остаётся отдельным, ненужным для этого);
- переупорядочивание СЕКЦИЙ брифинга по фокус-домену персонажа (список
  задач/привычек остаётся в том же порядке) — персонаж меняет голос
  AI-вставки, не структуру шаблонных списков;
- переключатель персонажа в боте — только сайт, по явному требованию
  владельца.

# План реализации

**Фаза 1 (эта итерация):**
1. `app/assistant/{models,repository,service,schemas,personas}.py`,
   миграция `021_create_assistant_settings`.
2. `app/core/container.py::build_assistant_service`.
3. Персонаж-параметр в пяти существующих генераторах (briefing/
   evening_reflection/finance_report/weekly_digest + новый chat_reply),
   расширение системных промптов и лимита длины ответа.
4. `app/conversation/chat_reply.py` + подключение в `ConversationEngine`
   как последний фолбэк перед `_HELP_TEXT`.
5. `app/api/assistant.py`, регистрация в `app/main.py`.
6. `/ui`: переключатель персонажа.
7. Тесты: repository/service/API/каждый из пяти генераторов с разными
   персонажами/дефолтом/None, chat_reply (успех + AI-сбой → откат на
   help).

**Фаза 2 (не сейчас, отдельная спека при необходимости):** более тесная
память диалога (хранение недавних реплик, не только Memory-записей),
редкие незапланированные сообщения персонажа, собственные имена.

# Definition of Done

- Все пункты бизнес-требований реализованы, кроме «Что НЕ входит».
- Тесты зелёные, ruff/black чисты.
- Миграция прогнана на проде.
- Проверено вручную владельцем: переключение персонажа на `/ui`,
  голос заметен в утреннем брифинге/вечернем вопросе/еженедельных
  отчётах, разговорный фолбэк отвечает по существу на нераспознанное
  сообщение (не просто список команд).
