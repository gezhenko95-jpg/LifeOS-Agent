# Voice Input Specification

---

# Цель

Голосовое сообщение в Telegram распознаётся в текст и обрабатывается
ТОЧНО так же, как если бы пользователь написал этот текст руками —
создание задачи, отметка привычки, дневник, всё, что умеет
`ConversationEngine`. Отдельного "голосового" intent'а нет — голос это
просто ещё один способ ДОСТАВИТЬ текст в уже существующий движок
(ADR-004: не изобретаем новую логику там, где хватает уже готовой).

STT — OpenRouter `/api/v1/audio/transcriptions` (запущен 22.07.2026),
тот же ключ и тот же `AIClient`, что уже используются для
`complete()`/`embed()` (см. `specs/003-conversation.md`,
`specs/011-semantic-memory-search.md`) — отдельного аккаунта/ключа не
требуется.

---

# Что НЕ входит

- Голосовые ОТВЕТЫ бота (text-to-speech) — только вход, бот как отвечал
  текстом, так и отвечает.
- Конвертация формата аудио — не нужна: Telegram отдаёт голосовые в OGG
  (кодек Opus внутри), а `ogg` — в списке официально поддерживаемых
  форматов и у OpenRouter, и у самого OpenAI whisper. Тащить `ffmpeg` в
  докер-образ бота ради конвертации незачем.
- `message.audio` (загруженные пользователем музыкальные/аудио-файлы) и
  `message.video_note` (кружочки) — это не голосовые заметки
  (`message.voice`), другой сценарий, вне скоупа.
- Локальный (self-hosted) Whisper — прод-сервер (Hostkey, Нидерланды) —
  2 vCPU, 1.8 ГБ RAM, из них уже занято ~230 МБ под bot+api+db.
  Приемлемая для русского модель (`small`) требует ~1-2 ГБ только под
  себя — риск деградации остального бота ради экономии копеек на
  облачном STT не оправдан.
- Многоязычность/явный выбор языка — модель сама определяет язык,
  проект и так на русском (см. остальные `specs/*.md`).

# Пользовательские сценарии

- Голосовое "напомни завтра купить молоко" → бот сначала показывает
  `🎤 «напомни завтра купить молоко»` (что расслышал), затем создаёт
  задачу — тот же ответ с кнопками, что и на текстовое сообщение.
- Голосовое дольше `voice_max_duration_seconds` (по умолчанию 5 минут)
  → `"Голосовое длиннее 5 мин — пришлите текстом."`, без похода в STT
  (не тратим деньги/время на заведомо нежелательный случай).
- OpenRouter недоступен/вернул ошибку → `"Не получилось распознать
  голосовое — попробуйте текстом?"`, ошибка логируется
  (`logger.warning`), пользователь не остаётся без ответа.
- Распознанный текст пустой (тишина/шум) → `"Не расслышал — тишина или
  не разобрал ни слова."`.
- `openrouter_api_key` не задан → `"Голосовой ввод ещё не настроен (нет
  ключа OpenRouter)."` — тот же паттерн "тихое отключение фичи + явное
  сообщение", что у Media Inbox без `token.json`
  (`specs/010-media-inbox.md`).

# Слои

## `app/ai/client.py`

`AIClient.transcribe(audio_bytes: bytes, audio_format: str = "ogg") -> str`
— base64 JSON через уже существующий `_post_json` (не multipart — тот
же путь, что у `complete()`/`embed()`), модель — отдельный параметр
конструктора `transcription_model` (по умолчанию
`openai/whisper-large-v3` — лучше `whisper-1` на русском). Таймаут
запроса длиннее обычного (60с вместо базовых 20с) — расшифровка
длинного голосового может занять больше времени, чем обычный
chat/embeddings-запрос.

`get_ai_client()` пробрасывает `settings.openrouter_transcription_model`
в конструктор, ключ кеша `AIClient`-инстансов дополнен этим полем.

## `app/core/config.py::Settings`

```python
openrouter_transcription_model: str = "openai/whisper-large-v3"
voice_max_duration_seconds: int = 300
```
Отдельного `voice_input_enabled` нет — фича включена неявно наличием
`openrouter_api_key` (`get_ai_client()` не `None`), как и остальные
AI-зависимые фичи проекта.

## `app/telegram/handlers.py`

`handle_voice_message(update, context)` — по образцу
`handle_photo_message` (скачивание файла, двухуровневая обработка
отказа: "фича не настроена" до похода в сеть / "не получилось" после).
Скачивание — `context.bot.get_file(voice.file_id)` +
`download_as_bytearray()`, как и у фото, без `asyncio.to_thread` (сам
вызов и HTTP-запрос к OpenRouter уже нативно `async`).

`_route_parsed_text(update, context, text)` — общий хвост маршрутизации
для текстовых (после проверки `_MENU_ACTIONS`, см. AUDIT.md A-6) и
голосовых (после транскрипции) сообщений: `parse_intent` →
LIST_TASKS/LIST_HABITS/LIST_WATCHLIST уходят с inline-клавиатурой,
остальное — в `ConversationEngine` через `_reply_via_engine`. Голос не
проходит через `_MENU_ACTIONS` — распознанный текст физически не может
буквально совпасть с текстом кнопки меню.

## `app/telegram/bot.py`

`application.add_handler(MessageHandler(filters.VOICE & owner, handle_voice_message))`
— рядом с уже существующим `filters.PHOTO`-хендлером, тот же
`owner`-фильтр (single-user, `PROJECT.md`).

# Definition of Done

- `AIClient.transcribe()`: успешный ответ, payload (base64 + формат +
  модель), не-200, битый JSON, сетевая ошибка, отдельный (больший)
  таймаут — `tests/ai/test_client.py`.
- `handle_voice_message`: фича не настроена, голос длиннее лимита,
  ошибка STT, пустая транскрипция, успешный путь (эхо распознанного
  текста + вызов `_route_parsed_text` с этим текстом) —
  `tests/telegram/test_voice.py`.
- `_route_parsed_text`: все три LIST-intent'а уходят с клавиатурой,
  остальное — в движок — `tests/telegram/test_voice.py`.
- Живая проверка после деплоя: отправить боту голосовое с простой
  задачей, убедиться, что приходит эхо распознанного текста и следом
  обычное подтверждение создания задачи с кнопками.
