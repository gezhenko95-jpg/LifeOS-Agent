# 1. Автоматический приоритет долгов

**Требование владельца:** снежный ком/лавина, но система сама определяет
приоритет — не переключатель стратегии, а готовый ответ «с какого долга
начать».

**Почему не настоящая лавина.** `Debt` не хранит процентную ставку (см.
specs/029 — решение не заводить её ради одной фичи). Настоящая лавина
(сначала самый дорогой по проценту) без этих данных невозможна. Вместо
выбора между двумя стратегиями — один автоматический алгоритм с двумя
уровнями:

1. **Срочность выше психологии.** Долг с `due_date` в пределах 30 дней —
   в приоритете, отсортированы по возрастанию даты. Пропущенный срок
   стоит реальных денег (пени/испорченная история) — это перевешивает
   любые бихевиористские аргументы за «маленький долг для мотивации».
2. **Иначе — снежный ком.** Долги без близкого срока сортируются по
   `remaining_amount` по возрастанию: наименьший остаток первым (быстрая
   психологическая победа) — стандартная рекомендация поведенческих
   финансов именно тогда, когда данных о ставке нет.

Закрытые долги (`remaining_amount <= 0`) не участвуют.

**Метод.** `DebtService.rank_by_priority(telegram_user_id) -> list[DebtPriority]`,
`DebtPriority(debt, rank, reason)` — `reason` человекочитаемый («срок
платежа скоро» / «меньше всего осталось»). API `GET
/finance/debts/priority`. `/ui`: список долгов пересортирован по этому
порядку, у первого — бейдж «🎯 приоритет — {reason}».

# 2. Сезонные/лимитированные украшения в Магазине

**Требование:** делаем.

`ShopItem` получает необязательное поле `available_until:
datetime | None = None` (по умолчанию — бессрочно, семь существующих
товаров не меняют поведение). `ShopService` исключает из витрины
товары, у которых `available_until` в прошлом И которые ни разу не
куплены — уже купленное украшение остаётся видно как «Куплено ✓», магазин
не стирает историю. `get_item()` (используется Фермой/Питомцем для
проверки владения уже купленным) остаётся БЕЗ фильтра — просроченный,
но купленный товар должен по-прежнему находиться.

Добавлен один пример — «🍂 Осенний шарф» (decor, 90 монет, до
20.09.2026) — чтобы механика была видна в проде не абстрактно, а
конкретным товаром. `/ui`: `⏳ до ДД.ММ` рядом с ценой, если
`available_until` задан.

# 3. «Приключения» питомца (Finch)

**Требование:** делаем.

**Триггер — питомец покормлен сегодня**, не отдельная проверка
задач/привычек: `PetService` уже знает `last_fed_at`, кросс-доменная
зависимость от tasks/habits не нужна. Раз в день (`Pet.last_adventure_on`,
миграция 040, дедуп тем же приёмом, что `hungry_notified_at`).

**Не отдельная джоба.** Довесок к `send_evening_checkin_job` (тот же
приём, что персонаж-нэджи specs/027 и утренняя рефлексия — «не плодить
новые cron-слоты ради небольшого дополнения»). Дедуп-отметка
(`record_adventure`) ставится ТОЛЬКО после успешной генерации текста —
слот один в день, поэтому при ошибке AI приключения в этот день просто
не будет, без ретраев (тот же trade-off, что уже принят у
персонаж-нэджей: тихий пропуск лучше, чем спам повторными попытками).

**Награда — монеты, не сено.** Сено — учёт грядок (harvested − consumed),
добавлять туда «сторонний» источник значило бы городить второй канал
начисления. Монеты уже нейтральный канал (см. `focus_reward` в
specs/029). Новый повод `pet_adventure` в `coin_transactions`. Шанс 40%,
3-10 монет — настоящий `random`, не детерминированный хэш: событие
разовое и фиксируется в ledger, в отличие от `total_coins`, который
пересчитывается заново при каждом запросе (детерминизм был нужен ИМЕННО
для пересчёта, здесь его нет).

**Текст — AI, голос персонажа.** `app/scheduler/pet_adventures.py`,
прямая копия паттерна `persona_nudges.py`: короткая (1 предложение)
история о находке на ферме, тихий `None` на ошибке AI (фича просто не
появляется в сообщении).

# 4. Квесты-боссы для целей (Habitica)

**Требование:** делаем.

**Только визуальный реskin существующего прогресс-бара** — не новый
элемент интерфейса. Прогресс цели (0-100%) уже есть, добавлена только
интерпретация: `%` — не «выполнено», а «урон по боссу». Эмодзи-статус
по тому же прогрессу, чистая функция на фронте, без нового поля:
0-24% — «Босс полон сил», 25-49% — «пошатнулся», 50-74% — «истощён»,
75-99% — «на издыхании», 100% — «повержен 🏆». Прогресс-бар остаётся
тем же элементом (не отдельная HP-полоска, чтобы не дублировать один и
тот же процент двумя виджетами).

**Награда за первую победу — один раз, не за каждое достижение 100%.**
`Goal.boss_reward_claimed_at` (миграция 041) — тот же принцип, что у
`Pet.deaths_count`: `GoalService` уже умеет снимать `COMPLETED`, если
прогресс утащили обратно ниже 100 (симметрия из specs/005), значит
без дедупа перетаскивание ползунка 100→90→100 фармило бы монеты
бесконечно. Флаг ставится один раз и не сбрасывается — заново цель
«побеждена» не будет, даже если статус опять станет `active`. Фиксированная
награда 25 монет (одноразовое событие, не требует калибровки под
частоту, как у чек-ина/фокус-сессий).

# 5. Взвешенные монеты за задачи

**Требование:** делаем.

**Вес — приоритет задачи**, единственное подходящее измерение, которое
уже есть на `Task` (`low`/`normal`/`high`). Награда: `{"low": 2,
"normal": 4, "high": 7}`. Дедлайн НЕ учитывается в весе — усложнение без
явного запроса владельца, приоритет уже даёт нужный сигнал «эта задача
важнее».

**Подзадачи не награждаются** (`task.parent_id is not None` → 0) —
без этого исключения ровно та критика Todoist Karma, которую нашло
исследование конкурентов (specs/029, преамбула): раздробить одну
задачу на пять подзадач стало бы выгоднее одной содержательной.

**Дедуп-риск принят, не закрыт кодом.** `Task` не хранит отдельного
флага «награда получена» — теоретически можно вручную выставить
`status=active` у уже завершённой задачи через API и завершить снова,
получив монеты дважды. Не реализовано в UI/боте как действие (нет
кнопки «переоткрыть»), а прямой вызов API — тот же класс риска, что уже
принят у гонки покупок в specs/028 («цена ошибки — несколько игровых
монет»); добавлять миграцию ради этого не стали.

**Реализация.** `TaskService` получает пятым опциональным аргументом
`shop_repository` (тот же приём, что три предыдущих домена). Награда
начисляется в обеих точках завершения (`update_task` при переходе
`active → completed`, `complete_task_by_title`) через общий приватный
метод.

# Общее

Все пять — расширения существующих доменов. Новых таблиц три (040 —
`Pet.last_adventure_on`, 041 — `Goal.boss_reward_claimed_at`, плюс
