# Три доработки вовлечения — по мотивам конкурентов

**Статус: реализовано (29.08, день #12).**

Владелец попросил посмотреть на конкурентов (Finch, Habitica, Duolingo,
Forest, YNAB/Monarch) и предложить, что ещё можно допилить для
пользователя в существующих плашках. Из предложенного списка выбраны
три пункта, каждый — расширение уже работающего домена, без новых
доменов и почти без новых таблиц:

1. **Калькулятор досрочного погашения долга** (Финансы, по мотивам YNAB).
2. **Стрик-заморозка привычек** (Привычки + Магазин, по мотивам Duolingo).
3. **Монеты за фокус-сессию** (Фокус-сессии, по мотивам Forest/TickTick —
   связывает домен, который сейчас изолирован от экономики монет).

---

# Цель

Все три — не новая механика ради новизны, а перенос конкретного приёма
конкурента на уже существующие данные/экономику LifeOS, без утяжеления
архитектуры новым доменом.

---

# 1. Калькулятор досрочного погашения долга

**Бизнес-требование.** У YNAB есть калькулятор: «добавь X₽/мес — закроешь
долг на N месяцев раньше». `Debt` уже хранит `remaining_amount` и
опциональный `monthly_payment` (план рассрочки) — процентной ставки в
модели НЕТ и добавлять её ради этой фичи не будем (владелец не вводит
проценты по каждому долгу вручную, а без ставки посчитать «сколько
сэкономлено на процентах» невозможно честно). Считаем только сдвиг срока
закрытия — это уже само по себе полезно и не требует новых данных от
пользователя.

**Пользовательский сценарий.** Открыл долг с планом рассрочки на `/ui`,
ввёл «сколько готов добавить сверху в месяц», увидел «закроете на N
месяцев раньше (было M, станет M−N)». Без плана рассрочки
(`monthly_payment is None`) — калькулятора нет, показывать нечего.

**Архитектура.** Чистая функция в `DebtService` — детерминированная
арифметика (ADR-004, тот же довод, что у `build_budget_recommendations`).
Никакой бизнес-логики в JS: `/ui` только вызывает эндпоинт и показывает
результат (тот же принцип, что во всех остальных карточках финансов).

```python
@dataclass
class PayoffPlan:
    months_current: int      # ceil(remaining / monthly_payment)
    months_with_extra: int   # ceil(remaining / (monthly_payment + extra))
    months_saved: int        # months_current - months_with_extra

async def simulate_payoff(
    self, telegram_user_id: int, debt_id: int, extra_monthly: int = 0
) -> Optional[PayoffPlan]:
    ...
```

`None` — долг чужой/не найден, или `monthly_payment` не задан (нечего
считать без плана рассрочки), или `remaining_amount <= 0` (уже закрыт).
`extra_monthly < 0` — `ValueError` (нет смысла «отрицательной доплаты»).

**Модели данных.** Ни одной новой таблицы и колонки — только чтение уже
существующих полей `Debt`.

**API.** `GET /finance/debts/{debt_id}/payoff-plan?telegram_user_id=&extra_monthly=0`
→ `PayoffPlanRead` или 404 (не найден/чужой/нет плана рассрочки — не
различаем причины отдельными кодами, все три «нечего посчитать»).

**UI.** В карточке «Долги», у долга с планом рассрочки — поле «доплата в
месяц» + кнопка «посчитать», результат текстом под долгом. Без
плана рассрочки поле не показывается вообще.

**План тестирования.** `DebtService.simulate_payoff`: обычный случай,
без плана рассрочки → None, чужой долг → None, extra=0 (текущий план
как есть, saved=0), долг закрыт (remaining=0) → None, отрицательная
доплата → ValueError. Плюс API: 200/404.

**DoD.** Тесты сервиса и API зелёные, ruff/black чисты, вручную проверено
на синтетическом долге (без бэкенда — как и весь /ui весь день #11).

# 2. Стрик-заморозка привычек

**Бизнес-требование.** У Duolingo заморозка стрика — платный предмет,
защищающий серию от одного пропущенного дня. Экономика монет уже готова
(`app/shop/`) — заморозка встаёт туда естественным новым товаром, не
новым доменом.

**Ключевое архитектурное решение — заморозка НЕ переписывает историю.**
Она защищает только ЧИСЛО текущего стрика (`current_streak`), не
добавляет фиктивную запись в `HabitLog`. Календарь привычки, рекорд серии
(`longest_streak`) и графики за период (`get_completed_days_bulk`)
остаются честными — там, где день не сделан, он и останется не сделан.
Тот же принцип, что уже применён к `Pet.deaths_count` (specs/028): игровая
поблажка не должна обесценивать честную память о факте. Раз в день
заморозка не «подделывает» выполнение — только не даёт погаснуть счётчику
серии.

**Что можно заморозить.** Только ВЧЕРАШНИЙ день, и только если это реально
помогает — то есть если позавчера привычка была отмечена (серия была
жива), а вчера — нет (иначе замораживать нечего: без соседней отметки
заморозка не продлила бы серию). Без ограничения «только вчера» владелец
мог бы годами копить заморозки и задним числом чинить любой давний
разрыв — не расходная механика поддержки текущей формы, а переписывание
истории пачками.

**Модель данных.** Миграция 039, `habit_streak_freezes`
(`habit_id` FK → `habits.id`, `protected_on: date`, `created_at`) —
append-only ledger, тот же приём, что `coin_transactions`/`debt_payments`.
Без `telegram_user_id`: владение проверяется через `Habit` (тот же
принцип, что у `HabitLog`).

**Товар в магазине** (`app/shop/catalog.py`), новый `kind = "freeze"`:
`id="streak_freeze"`, эмодзи 🧊, цена 40 монет (между семенем 30 и
ускорителем 45 — расходуемый предмет того же порядка), `repeatable=True`
(копится счётчиком, как семена).

**Composite.** `HabitService` получает третьим... вторым опциональным
аргументом `ShopRepository` (тот же приём, что у `FarmService`/
`PetService`) — считает доступные заморозки как
`purchased_counts["streak_freeze"] − количество использованных`.

**Сервис.**

```python
async def available_freezes(self, telegram_user_id: int) -> int: ...

async def freeze_yesterday(
    self, telegram_user_id: int, habit_id: int
) -> Habit:
    # 404 — чужая/не найдена привычка
    # 409 NoFreezeAvailable — инвентарь пуст
    # 409 NothingToFreeze — вчера уже отмечено, ИЛИ позавчера не было
    #     отметки (нечего продлевать), ИЛИ вчера уже заморожено раньше
```

`current_streak` для отображения серии — вызывается с
`completed_days | frozen_days`, не переопределяя сам
`app/habits/streaks.py` (он остаётся чистым и не знает о заморозках —
вызывающий код решает, что в него передать). `longest_streak` и
`get_completed_days_bulk` по-прежнему получают только `completed_days`
без объединения — рекорд и графики не должны показывать замороженный
день как выполненный.

**API.**
- `GET /habits/streak-freezes?telegram_user_id=` → `{available: int}`
- `POST /habits/{habit_id}/streak-freeze {telegram_user_id}` → `HabitRead`
  (свежий стрик уже с учётом заморозки) или 404/409.

**UI.** Строка в карточке «Магазин» (группа «Стрики», автоматически из
`KIND_TITLES`, без правок JS — витрина уже раскладывается по `kind`
сервера). В карточке «Привычки» — счётчик «🧊 доступно: N» над списком и
кнопка 🧊 у конкретной привычки, но ТОЛЬКО когда сервер говорит, что
заморозка реально поможет (`can_freeze_yesterday`, новое поле
`HabitRead`) — не показываем бесполезную кнопку у каждой привычки
всегда.

**План тестирования.** `streaks.py` не трогается — старые тесты
достаточны. `HabitService`: покупка → доступно N, использование убавляет
инвентарь, повторное использование того же дня → 409, без соседней
отметки → 409, пустой инвентарь → 409, `current_streak` с заморозкой
растёт, `longest_streak`/`get_completed_days_bulk` не видят
замороженный день. API: 200/404/409. Плюс `can_freeze_yesterday` в
бакетах true/false.

**DoD.** Тесты зелёные, ruff/black чисты, миграция применяется и
откатывается, магазин показывает новый товар без правок вёрстки (кроме
самих кнопок в Привычках).

# 3. Монеты за фокус-сессию

**Бизнес-требование.** Forest/TickTick связывают завершённую сессию с
наградой. У LifeOS фокус-сессии (`app/focus/`) сейчас изолированы от
экономики монет — заканчиваются, просто пишутся в статистику. Награда
привязывается к монетам (`coin_transactions`), не к сену: сено — ресурс
фермы/питомца, а фокус-сессии тематически ближе к «ежедневному визиту»
(рутина, не игровая мини-экономика).

`CoinTransaction.reason` уже спроектирован под это — докстринг модели
прямо говорит «в будущем, начисление мимо ежедневного чек-ина» (см.
`app/shop/models.py`). Новая константа `FOCUS_REWARD = "focus_reward"`,
`purchased_counts` фильтрует по `reason == PURCHASE`, так что новый повод
не попадёт в инвентарь магазина по ошибке — уже проверено существующим
кодом.

**Когда начисляется.** Только при переходе сессии в `COMPLETED` —
единственный путь `mark_break_notified` (опрашивающая джоба
`send_focus_notifications_job`, тот же процесс, что и уведомления
фермы/питомца). Отменённые сессии (`CANCELLED`) не награждаются.

**Формула — сознательно скромная, не конкурирует с чек-ином.**
- Базовая награда 5 монет за сессию, но только если `work_minutes >= 15`
  — короткие тестовые/дробные сессии не должны быть выгоднее одной
  длинной (тот же довод, что критика Todoist Karma в исследовании
  конкурентов: нельзя награждать объём вместо содержания).
- Бонус за серию ДНЕЙ (не сессий) — если это ПЕРВАЯ завершённая сессия
  сегодня, а не вторая-третья: `2 × min(стрик_дней, 5)` монет сверху
  (максимум +10). Стрик считается той же чистой функцией
  `current_streak` из `app/habits/streaks.py` над множеством дат, когда
  была хоть одна завершённая сессия — переиспользование, не копия.
- Итог: 5 монет за вторую+ сессию в день, 7-15 монет за первую (в
  зависимости от длины серии).

**Composite.** `FocusSessionService` получает опциональный
`shop_repository` (тот же приём, что `payment_repository` у
`DebtService` — без него старое поведение не меняется, существующие
тесты `FocusSessionService(repository)` не ломаются).

**Модели данных.** Ни одной новой таблицы — используется существующая
`coin_transactions` с новым значением `reason`.

**API.** Без нового эндпоинта — награда происходит побочным эффектом
внутри уже существующего потока `mark_break_notified` (только процесс
бота, единственный вызывающий код). Телеграм-сообщение о завершении
сессии дополняется суммой: «✅ Перерыв закончен... +N 🪙».

**UI.** Без немедленного обновления (сессии завершаются джобой бота, не
кликом на `/ui` — как и уведомления фермы/питомца, live-обновления карты
для них не делалось). Баланс в «Магазине» и так пересчитывается заново
при каждом открытии — новая транзакция уже видна при следующем визите.

**План тестирования.** `FocusSessionService.mark_break_notified` с
`shop_repository`: работа < 15 мин → 0 монет, первая сессия дня → база +
бонус по стрику, вторая сессия того же дня → только база, без
`shop_repository` — поведение не изменилось (старые тесты). Плюс
`purchased_counts` не видит `focus_reward` (реюз существующего теста
фильтра по `reason`).

**DoD.** Тесты зелёные, ruff/black чисты, реальное Telegram-сообщение
показывает начисленную сумму.

# Открытых вопросов владельцу нет

Все три калибровки (цена заморозки, формула фокус-награды, отсутствие
процентной ставки у долга) — решения по умолчанию с явным обоснованием
выше, тот же уровень автономности, что у калибровки фермы в specs/028,
где владелец не был против разумных значений по умолчанию, когда цифра
уже была явно посчитана и объяснена. Если что-то из калибровки не
понравится по факту использования — это правка констант, не архитектуры.
