# Tasks v2 Specification

---

# Цель

Три довеска к домену задач, запрошены владельцем одним заходом: статусы
за пределами готово/не готово, подзадачи/эпики, комментарии-лог. Первый
пункт из фазы «Задачи 2.0» большого бэклога правок `/ui` (23–24.08),
выбран первым, потому что от него зависят другие пункты бэклога
(привязка человека к задаче, просроченные отдельной графой, настройки
конкретной задачи, календарь — все они трогают ту же модель Task).

---

# Бизнес-требования (решения владельца)

Три развилки, уточнённые до реализации (не додуманы):

1. **Подзадачи** — полноценные дочерние задачи со своим статусом и
   сроком, привязанные к родительской (не чек-лист текстовых пунктов).
2. **Комментарии** — лог из нескольких записей с датой, не одна
   перезаписываемая заметка.
3. **«Большая задача»** — не отдельный тип, а обычная задача с
   подзадачами (эпик = задача с детьми, та же механика).
4. **Статус «в работе»** — независим от готово/не готово, задача может
   быть одновременно активной и «в работе».

# Архитектура

Расширение существующего домена `app/tasks/`, не новый домен: два новых
поля на `Task` (`in_progress`, `parent_id`) и новая модель `TaskComment`
в том же `models.py`. Один сервис на модель (ADR-005) —
`TaskCommentService` отдельно от `TaskService`, но с ownership-проверкой
через `TaskRepository` (комментарий принадлежит задаче, задача —
пользователю).

## Модель данных — довески к `Task`

| Поле | Тип | Комментарий |
|---|---|---|
| `in_progress` | bool, default false | НЕ третье значение `status` — иначе пришлось бы переписывать каждый запрос вида `status == "active"` (напоминания, дайджест, `find_active_by_title`) на «в {active, in_progress}». Отдельная колонка не трогает ни один существующий запрос. |
| `parent_id` | int, FK `tasks.id`, `ON DELETE CASCADE`, nullable | NULL — верхний уровень. Иерархия ПЛОСКАЯ: у подзадачи не может быть своих подзадач (проверка в `TaskService.create_task`) — два уровня достаточно для одного пользователя, рекурсивное каскадное удаление усложнило бы код без реальной пользы. |

## Новая модель — `TaskComment`

| Поле | Тип | Комментарий |
|---|---|---|
| `id` | int, PK | |
| `task_id` | int, FK `tasks.id`, `ON DELETE CASCADE` | |
| `telegram_user_id` | BigInteger | задел на мультиарендность (MULTIUSER.md) — авторитетна принадлежность задачи, не комментария |
| `text` | String(1000) | |
| `created_at` | DateTime(tz) | `server_default=func.now()` |

Миграция `022_tasks_v2` — обе правки одним файлом (тот же приём, что у
finance/CRM/mood: один довесок фичи — одна миграция).

## Список задач не захламляется подзадачами

`TaskRepository.list_by_user` получил `top_level_only: bool = False`;
`TaskService.list_active_tasks` (главный список — бот и `/ui`) передаёт
`True`. Подзадачи видны только через `list_subtasks(parent_id)` — но
по-прежнему находятся текстовым поиском (`find_active_by_title` не
фильтрует `parent_id`), поэтому «выполни <подзадача>» в чате работает
без отдельного UI.

Счётчики подзадач/комментариев на список — пачкой одним запросом
(`count_subtasks_by_parents`, `count_by_tasks`), не N+1 на каждую
задачу (AUDIT.md, тот же принцип, что уже применялся для limit'ов
памяти).

# Бот (Telegram)

Три новых действия в домене `t` (`app/telegram/keyboards.py`):

- `t|i|{id}` — переключить «в работе» (иконка ▶, ряд кнопок как у ✅/🗑)
- `t|a|{id}` — добавить подзадачу (pending input, `TASK_SUBTASK_ADD`)
- `t|k|{id}` — добавить комментарий (pending input, `TASK_COMMENT_ADD`)

`PendingInput` получил `task_id` (как `digest_id` у `DIGEST_CHANNEL`) —
контекст, к какой именно задаче относится следующее сообщение.

Список задач в тексте — бейджи `📎N`/`💬N` при наличии, `▶` перед
названием, если задача в работе. Просмотр СПИСКА подзадач/комментариев
(не только счётчика) в бота сознательно не вынесен отдельным экраном —
у флэт-списка задач нет концепции «открыть детали задачи», строить его
ради этого было бы отдельной фичей. `/ui` показывает и то, и другое
полностью (см. ниже) — бот для этого не единственный канал.

---

# `/ui`

Карточка «Задачи»: кнопка ▶ (заливается акцентом, когда включено),
бейджи 📎/💬 кликабельны наравне с шевроном ▾/▴ — разворачивают панель
под строкой задачи с двумя колонками (подзадачи + мини-форма добавления,
комментарии + мини-форма добавления). Панель лениво подгружает данные
(`GET /tasks/{id}/subtasks` + `GET /tasks/{id}/comments`) только при
раскрытии, не на каждую задачу списка сразу. Раскрытые панели переживают
перерисовку списка (Set id-шников, не индексов DOM).

# REST API (`app/api/tasks.py`)

- `POST /tasks` — принимает `parent_id`
- `GET /tasks/{id}/subtasks`
- `POST /tasks/{id}/in-progress` — переключить (без тела)
- `GET`/`POST /tasks/{id}/comments`
- `DELETE /tasks/comments/{id}`

`TaskRead` получил `in_progress`/`parent_id`/`subtask_count`/
`comment_count` — последние два не колонки модели, считаются пачкой и
проставляются в `app/api/tasks.py` поверх `model_validate`.

# Что НЕ входит (осознанно отложено)

- отдельный экран «детали задачи» в боте (см. выше);
- глубина иерархии больше двух уровней;
- редактирование/удаление комментария из бота (только `/ui` и API);
- награда (specs/016) за «в работе»/подзадачу/комментарий — это не
  «сделал»-действие в том же смысле, что выполненная задача;
- перенос комментария при перепривязке подзадачи к другому родителю —
  такой операции («переподвесить» подзадачу) вообще нет ни в одном
  интерфейсе.
