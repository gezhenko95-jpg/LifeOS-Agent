# Цель

Кому давно не писал и у кого скоро день рождения — без отдельного
приложения, без синхронизации контактов телефона. Владелец сам заводит
запись на человека (имя + опционально день рождения), сам отмечает
«написал(а)», а бот проактивно напоминает — тем же нэджевым механизмом,
что уже есть для целей и привычек (`app/scheduler/nudges.py`,
specs/008-nudges.md). Явно запрошено владельцем (см. HANDOFF, раздел «Что
сделать в начале новой сессии», п.3): «переиспользует существующий
proactive/nudges.py и паттерн доменов».

---

# Бизнес-требования

- завести контакт: имя (обязательно), день рождения (не обязательно, без
  года — трекается только повторяющаяся дата, не возраст), заметка
  (не обязательно) — через кнопку «➕ Добавить» в разделе «📇 Люди»;
- отметить «написал(а)» — одна кнопка у контакта, обновляет момент
  последнего контакта на «сейчас»;
- удалить контакт — кнопка, без подтверждения (как везде в проекте);
- список контактов — самые давние наверху (порядок = когда написать в
  первую очередь), с числом дней с последнего контакта;
- нэдж «давно не писал» — раз при пересечении порога (30 дней), не
  каждый день после;
- нэдж «день рождения скоро» — раз при пересечении порога (за 3 дня, за
  1 день, в сам день) — та же схема порогов, что у дедлайна цели
  (`_GOAL_DEADLINE_THRESHOLDS`);
- редактирование контакта (кроме отметки «написал(а)») и разбор
  «написал(а) с Аней» свободным текстом — не в этой итерации (см. «Что
  НЕ входит»).

# Архитектура

Седьмой домен по тому же шаблону, что tasks/habits/goals/watchlist/
finance: `app/crm/{models,repository,service,schemas}.py`. Добавление —
**только через кнопку** (`app/telegram/pending_input.py::CONTACT_ADD`),
не через общий `parse_intent` waterfall: в отличие от трат («потратил
500») у контакта нет естественной глагольной формы, которую безопасно
ловить где угодно в свободном тексте — риск ложных срабатываний выше
пользы (тот же компромисс, что у digest/journal-специфичных pending,
не общих intent'ов). Разбор текста после кнопки — новый модуль
`app/conversation/birthday_parser.py` (по образцу `amount_parser.py`):
извлекает дату вида «дд.мм» из остатка текста после имени, имя — то,
что осталось.

REST API и `/ui`-карточка — **в этой же итерации**, не отложены на
потом: урок из specs/017-finance.md (владелец не заметил кнопки без API/
`/ui` и попросил «полный арсенал» в тот же вечер) — не повторяем.

# Модель данных (`app/crm/models.py`)

## Contact

| Поле | Тип | Комментарий |
|---|---|---|
| `id` | int, PK | |
| `telegram_user_id` | BigInteger, indexed | владелец |
| `name` | String(100) | обязательно |
| `birthday_month` | int, nullable | 1–12, оба поля вместе или оба NULL |
| `birthday_day` | int, nullable | 1–31 |
| `notes` | String(500), nullable | |
| `last_contact_at` | DateTime(tz) | `server_default=func.now()` — свежий контакт не считается «давно не писал» с первого дня |
| `created_at` | DateTime(tz) | `server_default=func.now()` |

Год рождения не хранится: фича — напоминания, не учёт возраста. Отдельных
колонок под "month"/"day" вместо единого `date`, потому что SQL `date`
требует год, а год как раз то, чего часто нет (аналог решения по
категориям в finance — фиксированный список в коде вместо гибкости,
которая не нужна).

# Нэджи (`app/scheduler/nudges.py`, расширение)

Два новых условия рядом с существующими `_goal_deadline_nudges`/
`_habit_streak_break_nudges`, тот же приём «сработать РОВНО ОДИН раз при
пересечении порога»:

- `_stale_contact_nudges`: `days_since(last_contact_at) == 30` →
  `"👋 Давно не писал(а) «{name}» — {N} дней."`
- `_upcoming_birthday_nudges`: ближайшее вхождение (month, day) от
  сегодня, `days_left in (3, 1, 0)` → `"🎂 День рождения «{name}» — {когда}."`
  29 февраля в невисокосный год — ближайшее вхождение считается 1 марта
  (симметрично `_safe_date` в date_parser.py, но без прыжка на 28-е —
  1 марта ближе к duh «пропущенному» дню, чем 28 февраля).

`build_nudges` принимает опциональный `contact_service` (как остальные
сервисы в `send_nudges_job`) — `None` тихо отключает CRM-нэджи, тот же
паттерн опциональности, что у `ConversationEngine`.

# API (`app/api/crm.py`)

- `POST /crm/contacts` — создать
- `GET /crm/contacts?telegram_user_id=` — список, отсортирован по
  `last_contact_at` (давние сверху)
- `POST /crm/contacts/{id}/contacted` — отметить «написал(а)»
- `DELETE /crm/contacts/{id}`

---

# Бот (`app/telegram/`)

Пункт постоянного меню «📇 Люди» (`MENU_CONTACTS`) → экран раздела
(«📋 Список» / «➕ Добавить»). Домен callback_data — `c`:
- `c|m` — экран раздела, `c|l` — список, `c|n` — добавить (pending)
- `c|d|{id}` — отметить «написал(а)» (награда — «сделал»-действие, как
  отметка привычки), `c|x|{id}` — удалить (без награды)

---

# `/ui`

Восьмая вкладка «Люди», карточка со списком (давние сверху, значок ⚠️ у
тех, кто просрочил порог 30 дней — тот же токен `--overdue`, что у
финансов/задач) и формой добавления (имя + необязательная дата
рождения).

# Что НЕ входит

- редактирование контакта (кроме «написал(а)») — только удалить и
  завести заново;
- разбор «написал(а) с Аней»/«поговорил с Петей» свободным текстом —
  сопоставление имени с записью по нечёткому совпадению рискует
  перепутать контакты, надёжнее кнопка;
- импорт контактов телефона/Google Contacts;
- год рождения / возраст;
- своя картинка/иконка под пустое состояние раздела — переиспользуется
  существующий глиф (см. план реализации).
