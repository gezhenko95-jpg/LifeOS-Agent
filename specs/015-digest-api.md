# 015 — REST API дайджестов

## Зачем

Дайджесты Telegram-каналов (см. `013-channel-digests.md`) — единственный
домен, у которого нет REST API вообще: темы и каналы настраиваются только
командами бота. На `/ui` их не видно и не поменять.

Задача: дать сайту то же, что умеет бот, — список тем, создание темы,
добавление и удаление канала, отправку «прислать новое».

## Границы

**Входит:** пять эндпоинтов ниже, схемы Pydantic, форма на `/ui`.

**Не входит:**

- Удаление темы. Его нет и в боте — нечего переносить. Появится, когда
  понадобится, и сразу в обоих местах.
- Смена частоты у существующей темы. То же основание.
- Мультиарендность. Владелец по-прежнему один, `telegram_user_id`
  приходит параметром — как во всех остальных роутерах (см. `MULTIUSER.md`,
  там же про дыру с общим токеном).

## Эндпоинты

Все под `require_api_token`, как остальные защищённые роутеры.

| Метод | Путь | Смысл |
|---|---|---|
| `GET` | `/digest?telegram_user_id=` | Темы владельца, каждая со своими каналами |
| `POST` | `/digest` | Создать тему |
| `POST` | `/digest/{digest_id}/channels` | Добавить канал в тему |
| `DELETE` | `/digest/channels/{channel_id}?telegram_user_id=` | Убрать канал |
| `POST` | `/digest/{digest_id}/send` | Собрать дайджест и прислать в Telegram |

`GET /digest` отдаёт темы вместе с каналами одним ответом, а не отдельным
запросом на каждую тему: тем у человека единицы, а N+1 запросов ради
экономии одного JOIN — та самая проблема, которую уже чинили у привычек
(`AUDIT.md`, P-1).

## Отправка: главное решение спеки

`build_digest_text` **двигает водяной знак `last_seen_post_id` при сборке
текста**, и репозиторий коммитит сразу. То есть посты помечаются
прочитанными ДО того, как сообщение ушло в Telegram.

Для фоновой джобы это осознанный компромисс, он описан в её докстринге:
иначе при сбое отправки те же посты придут повторно. Но для кнопки на
сайте тот же компромисс даёт скверный сценарий: человек нажал, увидел
ошибку, а содержимое уже потеряно навсегда.

**Решение:** эндпоинт возвращает собранный текст в ответе всегда, а
доставку показывает отдельным полем.

```json
{ "delivered": true,  "text": "📰 Дайджест «ESG»\n\n…" }
{ "delivered": false, "text": "📰 Дайджест «ESG»\n\n…", "error": "…" }
{ "delivered": false, "text": null }
```

- Доставили → `delivered: true`, текст для показа на странице.
- Telegram не ответил → `delivered: false`, но **текст есть**: сайт
  показывает дайджест прямо на странице. Ничего не потеряно, хотя
  водяной знак уже сдвинут.
- Новых постов нет → `text: null`, страница пишет «новых постов нет».
  Не ошибка: ровно так же тихо пропускает джоба.

Переписывать порядок «сначала отправить, потом сдвинуть» здесь
намеренно не стали: это правка сервиса, которым пользуются ещё бот и
джоба, ради сценария, который лечится одним полем в ответе.

## Отправка из процесса API

API и бот — разные контейнеры, `context.bot` из джобы здесь недоступен.
Оба контейнера читают один `.env` (см. `docker-compose.yml`), то есть
`telegram_bot_token` у API есть.

Заводим `app/telegram/notifier.py` — отправка сообщения владельцу своим
экземпляром `telegram.Bot`, один на процесс (как `get_ai_client`: новый
объект на каждый запрос поднимал бы новое соединение).

Без токена в настройках эндпоинт отвечает `503` — тем же способом, что
и остальной API при пустом `api_token`: **отсутствие настройки закрывает
функцию, а не открывает её молча**.

## Новое в сервисе

Две тонкие обёртки, симметричные уже существующему
`remove_channel_by_id`:

- `add_channel_by_id(user, digest_id, channel_username)`
- `build_digest_text_by_id(user, digest_id, ai_client)`

Нужны потому, что сайт оперирует **id**, а существующие методы принимают
**имя темы**. Резолвить id в имя в роутере нельзя: там проверка
владельца, а роутеры в этом проекте бизнес-логики не содержат.

## Ошибки

| Ситуация | Ответ |
|---|---|
| Тема с таким именем уже есть, имя пустое или из двух слов | `400` |
| Канал уже в теме, канал не читается | `400` |
| Тема или канал не найдены (или чужие) | `404` |
| Нет `telegram_bot_token` | `503` |

Чужой объект неотличим от несуществующего — `owned_or_none`, тот же
принцип, что во всём проекте.

## Проверка

- Тесты роутера на каждый эндпоинт, включая `404` на чужую тему.
- Отправка: доставлено, не доставлено (Telegram кинул исключение),
  постов нет, токена нет.
- Миграции не нужны — таблицы из `014` уже на проде. Значит и
  scratch-проверки на сервере не требуется.
