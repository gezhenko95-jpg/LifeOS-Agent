# Personal Insights Specification

---

# Цель

Дать пользователю то, чего не даёт ни утренний брифинг (про сегодня), ни
недельный дайджест (сырые цифры за неделю): **поведенческие
закономерности**, видимые только на длинном горизонте (60 дней) — когда
он реально продуктивен, помогает ли ему дневник держать привычки, и
успевает ли он к своим дедлайнам. Закрывает Phase 5 (`ROADMAP.md`) —
"Personal Insights" / "Productivity Analytics".

Согласно ADR-004, все находки — детерминированные вычисления над уже
существующими таблицами (`tasks`, `habit_logs`, `memory_entries`), без
LLM. LLM в этой фиче не участвует вообще: находки — статистика, а не
понимание естественного языка, значит простой код предпочтительнее (это
даже более чистый случай ADR-004, чем брифинг/дайджест).

---

# Что НЕ входит

- Никакой AI-фразы поверх находок (в отличие от брифинга/дайджеста) —
  осознанное решение, см. "Цель".
- Графики (v1 — только текст). Тепловая карта/бар-чарт по дню недели —
  идея на будущее, не блокирует v1.
- Кросс-пользовательские сравнения ("ты продуктивнее среднего") — бот
  однопользовательский (`owner_telegram_user_id`), сравнивать не с кем.
- Причинно-следственные выводы — находки формулируются как корреляции
  ("в дни с дневником привычки выполняются чаще"), не как утверждения о
  причине.

# Находки (v1, все за скользящее окно 60 дней)

1. **Продуктивный день недели** — распределение `Task.completed_at` по
   дням недели. Показывается, только если завершено ≥ 10 задач за окно
   (иначе выборка слишком мала, чтобы день недели что-то значил).
   Формулировка: "Чаще всего задачи закрываются по вторникам (32%),
   реже всего — по субботам (4%)."
2. **Дневник и привычки** — среди дней окна, где есть хотя бы одна
   привычка к отслеживанию: доля выполненных привычек в дни С
   журнальной записью против дней БЕЗ неё. Показывается, только если в
   окне есть ≥ 5 дней каждого типа (с записью / без). Формулировка: "В
   дни, когда ты пишешь дневник, привычки выполняются в 1.8 раза чаще
   (68% против 38%)."
3. **Дисциплина по срокам** — среди завершённых задач с `due_date`:
   доля завершённых после дедлайна + средняя задержка (только по
   просроченным). Показывается, только если таких задач ≥ 5.
   Формулировка: "7 из 12 задач со сроком в этом окне закрыты позже
   дедлайна, в среднем на 2 дня."
4. **Самая длинная серия привычки** — `max(longest_streak)` по всем
   активным привычкам (не только текущий стрик, а рекорд за всё время
   логов). Показывается, только если есть хотя бы одна привычка с ≥ 1
   логом. Формулировка: "Рекорд серии — «Чтение», 14 дней подряд."

Если ни одна находка не набрала данных для показа — сообщение "Пока
маловато данных для инсайтов, возвращайся позже" (для команды/кнопки;
для фонового месячного запуска в этом случае просто ничего не
отправляется, тихий пропуск).

# Архитектура

Новый изолированный модуль `app/insights/` (ADR АГЕНТС.md п.2.4 — каждая
возможность — отдельный сервис), **без своей таблицы** — только
композиция чужих сервисов/репозиториев, как уже делает
`app/scheduler/weekly_digest.py`:

- `app/insights/service.py` — `InsightsService(task_service, habit_service,
  memory_service)`, метод `async def build_findings(telegram_user_id) ->
  list[str]` — возвращает 0..4 готовые фразы (без AI). Каждая находка —
  приватный метод (`_productive_weekday`, `_journal_habit_correlation`,
  `_deadline_discipline`, `_longest_streak`), чтобы файл не разрастался
  (лимит 250-300 строк, АГЕНТС.md п.2.5) — при необходимости выносятся в
  `app/insights/calculations.py` (чистые функции без БД, легко
  тестируются без моков — та же схема, что `charts.py`:
  `gather_chart_data` / `render_chart`).
- `app/insights/formatting.py` — `build_insights_text(findings: list[str])
  -> str` — обёртка "Инсайты за последние 60 дней:" + буллеты, либо
  фолбэк-фраза про нехватку данных.

## Требуемые расширения существующих репозиториев

- `TaskRepository.list_completed_between(uid, since, until) -> list[Task]`
  — по образцу уже существующего `count_completed_between`, но
  возвращает сами строки (нужны `completed_at` и `due_date` для находок
  1 и 3).
- `MemoryRepository.list_by_type_since(uid, type, since) -> list[MemoryEntry]`
  — по образцу `count_completed_since` на задачах; нужны только даты
  создания journal-записей для находки 2.
- `HabitService.get_longest_streak(habit_id) -> int` — рекорд самой
  длинной последовательности подряд идущих дат в `get_completed_days`
  (уже есть, метод чистый, без новых запросов к БД). Отличается от
  существующего `get_streak` (тот — только текущая, не обязательно
  рекордная серия).

Всё остальное — чтение уже существующих методов сервисов.

# Доставка пользователю

Два способа получить один и тот же текст — специально не завязываемся
на что-то одно, чтобы не плодить новый "6-й слот" в дневном ритме
(`flows/009-daily-rhythm.md` был про то, что слотов остаётся 5):

1. **По запросу** — кнопка "📊 Инсайты" в главном меню
   (`app/telegram/keyboards.py`) → `_MENU_ACTIONS` в `handlers.py`
   вызывает `InsightsService.build_findings` + `build_insights_text`,
   отправляет сообщением. Если находок нет — фраза про нехватку данных
   (см. выше).
2. **Раз в месяц, не спрашивая** — `send_monthly_insights_job`
   (`app/telegram/jobs.py`), первое число месяца, время из настроек
   (`monthly_insights_hour`, по умолчанию 12:00, чтобы не пересекаться с
   существующими 5 слотами `flows/009-daily-rhythm.md`). Если находок
   нет — тихий пропуск (не шлём "недостаточно данных" в фоновом
   режиме — это шум, см. `PROJECT.md`: "Простота").

Регистрация в `app/telegram/bot.py`: `run_monthly`-подобный вызов (PTB
`JobQueue` не имеет "раз в месяц" из коробки — используется `run_daily`
с проверкой `date.today().day == 1` внутри джобы, тот же приём, что уже
применяется для воскресного дайджеста через `days=(6,)`, но с
дневным фильтром внутри тела функции, т.к. "day == 1" не выразить через
`days=`).

Новые настройки в `app/core/config.py`: `monthly_insights_enabled`
(default `True`), `monthly_insights_hour` (default `12`),
`monthly_insights_minute` (default `0`).

# План тестирования

- `calculations.py` (чистые функции, без БД, без моков):
  - `productive_weekday`: пусто → `None`; < 10 задач → `None`; явный
    перекос по дню → правильный день и процент; равномерное
    распределение — не падает.
  - `journal_habit_correlation`: < 5 дней одного из типов → `None`;
    явная корреляция → правильные проценты и множитель; деление на
    ноль (0 дней без дневника) не роняет функцию.
  - `deadline_discipline`: < 5 задач со сроком → `None`; все вовремя →
    "0 из N"; смешанный кейс — правильная доля и средняя задержка.
  - `longest_streak`: пустой набор дат → 0; один день → 1; несколько
    несмежных отрезков → берётся самый длинный, а не последний.
- `InsightsService.build_findings`: интеграционный тест на SQLite
  in-memory — 0 находок (пустая БД) → `[]`; частичные данные (например,
  только привычки, без задач) → только релевантные находки, без
  падений на отсутствующих.
- `build_insights_text`: пустой список → фраза про нехватку данных;
  1-4 находки → буллеты, каждая на своей строке.
- Хендлер кнопки "📊 Инсайты" — по образцу существующих тестов
  `_MENU_ACTIONS` в `tests/telegram/test_handlers.py`.
- `send_monthly_insights_job` — по образцу `send_weekly_digest_job`:
  вызывается только 1-го числа (мок `date.today()`), пустые находки →
  `send_message` не вызывается.

# Definition of Done

- Все находки покрыты граничными случаями (мало данных / деление на
  ноль / пусто) — не только "счастливый путь".
- `pytest`/`ruff`/`black` зелёные.
- Живая проверка в контейнере: кнопка "📊 Инсайты" на реальных данных
  владельца отдаёт осмысленный (или корректно пустой) текст; ручной
  вызов `send_monthly_insights_job` с замоканной датой "1 число" отдаёт
  то же самое сообщением.
